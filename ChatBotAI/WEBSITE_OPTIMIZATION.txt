[x] STEP 7 — Duplicate-messages fix (2026-05-13)
    Investigation found that 38bff2d (HTML-strip in content dedup) was
    correct but addressed a DIFFERENT bug. Active duplicates were still
    happening: 15 platform_message_id duplicate pairs since 2026-04-22,
    with sub-millisecond gaps between rows → classic race condition.

    Root cause: three concurrent sync paths (background daemon + manual
    full-sync route + per-conversation sync route) all run the same
    check-then-insert pattern. With NO UNIQUE constraint on
    platform_message_id, two threads could both pass the "not in DB"
    check and both insert before either committed.

    Fix:
      a) Migration p14_uniq_platform_msg_id:
         - Repointed 8 conversation.last_read_message_id pointers from
           soon-to-be-deleted dup rows to their surviving lower-id sibling
         - Deleted 15 duplicate message rows (kept MIN(id) per plat_id)
         - Created partial UNIQUE INDEX
           ix_message_platform_message_id_unique
           ON message (platform_message_id)
           WHERE platform_message_id IS NOT NULL
      b) Code: services/smoobu_service.py (2 sites) and
         services/message_router.py (_store_message) now catch
         IntegrityError on insert. On collision they roll back and
         either skip (smoobu sync) or return the winning row
         (message_router) so callers see a consistent result.

    DB backed up to instance/chatbot.db.bak-pre-p14-20260513-120632.
    Verified: 24/24 tests pass; manual INSERT of dup platform_message_id
    raises IntegrityError as expected; 0 dupes remain.

[x] STEP 7c — Cold-cache morning-load mitigation (2026-05-15)
    Symptom: after server idles overnight, first page load next morning
    feels slow even though Cloudflare cache rules are in place. Reason:
    Cloudflare edge cache cools off without traffic, CF tunnel may need
    re-handshake, SQLite pages get evicted from the OS file cache.

    Fix has two parts:
      a) SQLite pragmas (app.py _setup_sqlite_pragmas):
         - PRAGMA cache_size=-65536    (64MB in-process page cache)
         - PRAGMA mmap_size=268435456  (256MB memory-mapped IO)
         Keeps more DB pages hot in memory so first queries after idle
         don't hit cold OS file cache.
      b) Keepalive daemon (_start_keepalive in app.py):
         - Pings KEEPALIVE_URL every KEEPALIVE_INTERVAL seconds (5 min)
         - Default URL: https://umteamsbz.com/chatbot/api/keepalive
         - New endpoint /chatbot/api/keepalive does a 1-row DB touch
           and returns 200 JSON. No Ollama call (avoids cloud charges).
         - Whitelisted past login wall so anonymous requests succeed.
         - Outbound hit goes through the whole chain: CF edge → CF tunnel
           → Waitress → Flask → SQLite → keeping each layer warm.
    Set KEEPALIVE_URL='' to disable. Tests pass.

[x] STEP 11 — Missing-messages bug (2026-05-15)
    User reframed the symptom: girls on phones don't see new messages
    in the inbox, but the message IS in the DB (user verified by opening
    the conversation on PC).

    Root cause: the inbox poller (`inbox.js` `inboxPoller`, every 3s) only
    triggers a full inbox refresh when `MAX(conversation.updated_at)` OR
    `unread COUNT` changes (via `/api/conversations/last-updated`).

    `MessageRouter.process_incoming_message` had logic that only bumped
    `conversation.updated_at` when the new message's `sent_at` was newer
    than the current `updated_at`. For out-of-order Smoobu deliveries
    (e.g. a guest reply with a timestamp older than our last owner
    message), `updated_at` did NOT move. And because the conversation
    was already unread, the unread count didn't change either. Result:
    poller never fired, inbox preview stayed stale forever — on every
    device — even though the conversation page (which loads messages
    directly) showed the truth when opened.

    Why this looked phone-specific: girls sit on the inbox waiting for
    the unread badge / preview to update; PC users open conversations
    more often and stumble into the actual messages.

    Fix (services/message_router.py): always advance `updated_at` so
    the poller fires. For forward-in-time messages use `msg_ts`
    (truthful); for out-of-order ones use `max(old_updated_at, now())`
    so the conversation still surfaces in the inbox without lying
    about the message time. `is_read` logic preserved: forward = mark
    unread; out-of-order = recompute from read cursor.

    Owner-message paths in services/smoobu_service.py left untouched —
    they already trip the unread-count tripwire by setting is_read=True,
    so the bug doesn't manifest there, and bumping updated_at on a slow
    owner-echo sync could cause weird inbox reorderings.

Log in to https://dash.cloudflare.com → select domain `umteamsbz.com`.

A) Cache Rules (Caching → Cache Rules → "Create rule"):

   Rule name : Cache static assets
   When incoming requests match :
       URI Path  starts with  /chatbot/static/
       OR
       URI Path  starts with  /static/
   Then :
       Cache eligibility       : Eligible for cache
       Edge TTL                : Override origin → 1 month
       Browser TTL             : Override origin → 1 week

   Save and deploy.

B) Tiered Cache (Caching → Tiered Cache):
   Enable "Smart Tiered Cache Topology".

C) (Optional) Compression (Speed → Optimization → Content Optimization):
   Brotli ON (defaults to ON usually).

VERIFICATION
   After saving, hard-reload the app and check response headers in DevTools:
       cf-cache-status: HIT       (after second request)
       cache-control: public, max-age=...
   If you see DYNAMIC instead of HIT, the rule didn't match — re-check
   the URI path matcher.

NOTES
   - Existing ?v= versioning (style v49, etc.) means cache-busting is
     already in place. Bumping the ?v= number forces a refresh.
   - Do NOT cache /chatbot/api/* or HTML pages — only /static/.
